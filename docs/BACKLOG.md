## [ ] 1. Импорт: разбор адресов с «район/поселок» + чистка существующих

**Проблема.** `App\Services\PlanningRequest\ExcelRequestParser::parseAddressString` умеет только
формат «город, улица, дом». Для «город Москва, **район Внуково**, улица Анны Ахматовой, д. 18»
он кладёт всё после города в `street` (= «район Внуково, улица Анны Ахматовой»), а `district`
оставляет пустым. Срез ведущего «улица» (`AddressMatcher::stripLeadingStreetType`) тут не помогает —
ведущее слово «район». Такие записи к тому же — скрытые дубли «чистых» адресов (напр. «район Внуково,
улица Анны Ахматовой / 18» дублирует уже существующий «Анны Ахматовой / 18, посёлок Внуково»),
которые `addresses:merge-duplicates` не склеивает (сравнивает точный текст улицы).

**Важно не сломать.** Легитимные адреса Новой Москвы, где «посёлок X» / «микрорайон X» — само место
(улицы нет), и `district` заполнен. Их трогать нельзя. Чистить только записи с ведущим «район» и
**пустым** `district`, по списку id, а НЕ по маске.

- [ ] Доработать `parseAddressString`: распознавать ведущий «район …[, поселок …]», выносить район в `district`, оставлять настоящую улицу в `street`. Определить правило для New-Moscow без улицы.

## [x] 3. Оборудование под бригадой: «живой» режим без лага (рефреш при загрузке)

**Реализовано 2026-06-22** (локально, тесты 10/10, проверено Playwright) — ждёт ручной проверки и деплоя.

**Контекст.** Оборудование (комплект H-* + машина) показывается рядом с бригадой для ОТКРЫТЫХ
заявок только за сегодня; данные в `request_equipment` наполнялись командой `wms:refresh-equipment`
(`->hourly()`), при закрытии — заморозка. Минус был: лаг до часа между выдачей и появлением.

**Важно (выяснено при отладке):** дневную таблицу на загрузке перерисовывает `handler.js`
(fetch `/api/requests/date/{today}` = `getRequestsByDate`) и сам рендерит оборудование из
`request.equipment`. Поэтому JS-инъекция своего блока бесполезна (перетирается). Правильное
решение — делать **данные свежими на сервере**, и тогда и серверный рендер, и handler.js покажут свежее.

**Сделано (серверный подход):**
- [x] `WmsEquipmentService::refreshTodayBestEffort()` — обновляет `request_equipment` открытых
      сегодняшних заявок из склада. Вызывается в `HomeController::index()` и `getRequestsByDate()` (за сегодня),
      перед отдачей данных. Так при перезагрузке инвентарь свежий сразу после выдачи, а не раз в час.
- [x] Троттл 30 сек (`Cache` `wms_equipment_refreshed_at`) — частые F5 склад не долбят.
- [x] Безопасность главной: быстрый пинг склада (2 сек) — недоступен → выходим, страницу не вешаем; всё в try/catch.
- [x] Cron `wms:refresh-equipment` оставлен `->hourly()` как «пол».
- [x] Прод-инфра: планировщик Laravel в crontab настроен 2026-06-22 (`sudo -u www-data … schedule:run`), см [[prod-scheduler-www-data]].
- [x] Проверено Playwright: протухший маркер на перезагрузке перезаписывается реальными данными склада;
      при активном троттле — рефреш пропускается (склад не дёргается).
- [ ] (Опц., НЕ делали) «по-настоящему живое» без F5 (поллинг/пуш) + батч-эндпоинт на складе —
      только если per-load опрос станет узким местом.

     иначе `LIKE '%%'` вернёт всё.

## Блок 5 — мобильная вёрстка «Заявок» и «Планирования» (07.08.2026)

### Что просил заказчик (дословно из ТЗ)
- «Сверстать мобильное отображение для этих двух вкладок **по образу и подобию** уже
  адаптированной мобильной версии вкладки Отчёты».
- «Спроектировать новое расположение чекбоксов… чтобы они не перекрывали контент и по ним
  было удобно попадать пальцем». Рекомендация заказчика: правый верхний угол карточки
  **или** режим «Выбор» по долгому нажатию.

### Причина проблемы
Обе таблицы на телефоне оставались таблицами с фиксированными ширинами колонок в
`mobile-requests.css`: `col-number 2rem + col-address 8rem + col-comments 10rem +
col-brigade 8rem ≈ 450px` при экране 375px. Отсюда горизонтальная прокрутка и обрезанный
текст. На «Отчётах» этого нет, потому что там строка разворачивается в карточку.

### Что сделано
- `public/css/mobile-requests.css`: удалены фиксированные ширины колонок, добавлен блок
  карточной раскладки для `#requestsTable` и `#requestsPlanningTable` (строка → карточка,
  ячейки в столбик, «Бригада» — подвал с разделителем, фон карточки берётся из
  `--status-color`, т.е. цветовая маркировка статусов сохранена).
- **Один набор правил на обе вкладки** — классы колонок (`col-number`, `col-address`,
  `col-comments`, `col-brigade`) совпадают в Blade и в ОБОИХ JS-рендерах
  (`handler.js`: дневная таблица ~стр. 131 и планирование ~стр. 1211). Проверено.
- **Чекбокс — правый верхний угол карточки** (вариант из ТЗ). Ячейка `col-number`
  разворачивается в строку: номер слева, чекбокс справа. Видимый размер 22px,
  зона нажатия расширена псевдоэлементом `::after` до **44×44** (рекомендация
  Apple HIG / Material) — требование «удобно попадать пальцем» без раздувания вёрстки.
- Тёмная тема: рамки карточек и разделители переключаются на светлые.

### Почему НЕ долгое нажатие (long press)
Заказчик оставил выбор за разработчиком. Отклонили, потому что:
1) скрытый жест не обнаруживается — оператор решит, что массовые действия пропали;
2) конфликтует с системным выделением текста и контекстным меню на Android;
3) залипающая панель массовых действий (блок 1) висела бы неактивной без объяснения;
4) видимый чекбокс совпадает с десктопом — не надо переучиваться.

### Важно: пойманная при работе регрессия
На «Отчётах» шапка таблицы скрывается целиком (`thead { display: none }`). Скопировав
этот приём, мы бы **убрали глобальный чекбокс «Выбрать все»** из блока 1 ТЗ — он живёт
в первой ячейке `thead`, и массовые действия на мобильном стали бы недоступны.
Решение: шапка не прячется, а сжимается в узкую полоску (34px) — только ячейка
`.th-select-all` с чекбоксом и подписью «Выбрать все» (`<label for>`, клик по тексту
переключает). В `welcome.blade.php` к обоим `<th>` добавлен класс `th-select-all`
и мобильная подпись `.select-all-label` (`d-md-none`).

### Проверено
Изолированный стенд с настоящими CSS и разметкой (в `storage/app/public/`, вне гита,
после проверки удалён), viewport 375×812:
- горизонтальная прокрутка отсутствует: `scrollWidth 375 == innerWidth 375`;
- зона нажатия чекбокса `44px × 44px`, отступ от края карточки 14px;
- клик по подписи «Выбрать все» переключает чекбокс;
- тёмная тема: `rgba(255,255,255,.15)` на рамках;

прокрутки нет.

### Не проверено на реальном телефоне
Локальный дев-сервер стабильно отдаёт `ERR_EMPTY_RESPONSE` на телефон — причина
установлена и к коду отношения не имеет: в локальной БД 90 487 записей о фото, а файлов
на диске 17 (пользователь сознательно не тянет медиа с прода — занимает место). Каждый
промах по файлу проваливается в Laravel вместо отдачи статики и кладёт встроенный сервер.
На проде nginx отдаёт статику сам — проверять там.
