## Принятые решения
- **Одна VM** на новый стек (как сейчас на `.10`), не дробим по ролям.
- Datastore: **`raid5-4.4tb`**.
- Финальное переключение трафика — **в короткое ночное окно** (даунтайм на минуты), не blue-green.
- IP новой VM — получить по DHCP при установке, затем закрепить статической резервацией на MikroTik
  (тот же паттерн, что и у `.10`), а не прописывать вручную.
- **Zabbix — отдельная VM**, не в общем стеке. Причина: мониторинг не должен падать вместе с тем,
  что он мониторит (если основная VM ляжет — Zabbix на ней тоже ляжет и не пришлёт алерт именно
  тогда, когда это важнее всего). Ресурсы на Dell позволяют — не про нагрузку, а про надёжность.
- При переносе Zabbix — поставить **TimescaleDB** (расширение Postgres, официально поддерживается
  Zabbix для `history`/`trends`): автосжатие/ретеншн старых метрик, быстрее запросы по мере роста
  данных. Ставить сразу на новом окружении — дешевле, чем переделывать потом на живых данных.

## Физическая репликация PostgreSQL (main-кластер)

**Решение ОБНОВЛЕНО ПОВТОРНО 2026-07-22 (вернулись к варианту с `.10`):**
Между 2026-07-10 и сейчас план по реплике сменился дважды:
1. Исходно (до 07-10): временный `.10` (primary) → `.55` (replica), потом менять роли местами.
2. 07-10: отказались от `.10` в схеме репликации вообще — решили, что после переезда `.10`
   становится чистым jump host + Zabbix, а реплика едет на `.55` (обе VM на одном Dell).
3. **07-22 — вернулись к `.10` как реплике** (обсуждение с Gemini + подтверждено пользователем
   «оставим наш старый вариант с .10»): физически `.10` — ДРУГОЕ железо, чем Dell, поэтому реплика
   именно там даёт реальную защиту от отказа Dell (то, чего вариант с `.55` не давал — обе VM были
   бы на одном хосте). Это как раз то, что раньше было отмечено как «отдельный вопрос на будущее» —
   пригодилось раньше, чем ожидали.

**Итоговая схема:** `lan-install-new` (`.67`, primary, Dell) → `.10` (replica, старое железо,
физически отдельное от Dell).

**Судьба `.10` после переезда:** тройная роль — **jump host + Zabbix + реплика PostgreSQL**
(вместо изначально планировавшихся jump host + Zabbix без БД).

**`.55` (`pg-replica`)** — VM создана и ждёт (Debian 12, IP закреплён на MikroTik, SSH настроен),
но в актуальном плане **не используется** для этой репликации. Не трогаем/не удаляем — решить
её судьбу отдельно (про запас на будущее, второй реплика-узел, или вообще не нужна — уточнить
с пользователем, когда дойдём до этого шага).

## Эксплуатация

### Runbook: расширение дискового места на `.67`

**Контекст.** ВМ выдан диск **600 ГБ** (`/dev/sda`, один раздел `sda1` ext4 под `/`, без LVM).
Под ним — датастор `raid5-4.4tb` со **свободными ~4.31 ТБ**, так что расти есть куда.
Основной потребитель — фотоотчёты `storage/app/public` (на 2026-07-24 — 194 ГБ, постоянно растут).

⚠️ **Важная деталь раскладки.** swap (`sda5`, внутри extended `sda2`) лежит **в хвосте диска,
после `sda1`**. Значит новое место от увеличения VMDK появится в самом конце, **за swap**, и
`growpart /dev/sda 1` в лоб не расширит корень. Отсюда два пути:

#### Вариант А (рекомендуется) — отдельный диск под фото, без хирургии над корнем

Низкий риск, всё онлайн, не трогаем `sda`/swap.

1. **ESXi:** добавить ВМ второй жёсткий диск (напр. 1 ТБ, thin, датастор `raid5-4.4tb`).
2. **На `.67`** — найти новый диск и разметить:
   ```bash
   lsblk                                   # убедиться, что новый диск = /dev/sdb (проверь!)
   sudo parted -s /dev/sdb mklabel gpt mkpart primary ext4 0% 100%
   sudo mkfs.ext4 -L photos /dev/sdb1
   ```
3. Перенести фото на живой системе (несколько проходов rsync, потом короткое окно):
   ```bash
   sudo mkdir -p /mnt/photos-new && sudo mount /dev/sdb1 /mnt/photos-new
   sudo rsync -aHAX --info=progress2 /var/www/lan-install/storage/app/public/ /mnt/photos-new/
   # финальный досинк (быстрый, доганяет изменения):
   sudo rsync -aHAX --delete /var/www/lan-install/storage/app/public/ /mnt/photos-new/
   sudo umount /mnt/photos-new
   ```
4. Смонтировать новый диск на место фото:
   ```bash
   sudo mv /var/www/lan-install/storage/app/public /var/www/lan-install/storage/app/public.old
   sudo mkdir /var/www/lan-install/storage/app/public
   sudo mount /dev/sdb1 /var/www/lan-install/storage/app/public
   sudo chown www-data:www-data /var/www/lan-install/storage/app/public
   ```
5. Автомонтирование в `/etc/fstab` (по UUID, стабильнее имён):
   ```bash
   sudo blkid /dev/sdb1                     # взять UUID
   echo 'UUID=<uuid>  /var/www/lan-install/storage/app/public  ext4  defaults,nofail  0  2' | sudo tee -a /etc/fstab
   sudo mount -a && df -hT /var/www/lan-install/storage/app/public
   ```
6. Проверить сайт (фото открываются) → потом удалить резерв: `sudo rm -rf /var/www/lan-install/storage/app/public.old`.

#### Вариант Б — нарастить сам корень `/` (одна ФС, но нужна возня со swap)

Годится, если хочется всё держать на одном разделе. Риск выше (правка таблицы разделов
загрузочного диска), делать вдумчиво, лучше со снапшотом ВМ в ESXi.

1. **ESXi:** увеличить существующий VMDK до нужного размера (напр. 1.5–2 ТБ), снять снапшот ВМ.
2. **На `.67`** — заставить ядро увидеть новый размер без ребута:
   ```bash
   echo 1 | sudo tee /sys/class/block/sda/device/rescan
   ```
3. Убрать хвостовой swap, чтобы свободное место стало смежным с `sda1` (переводим swap в файл):
   ```bash
   sudo swapoff /dev/sda5
   sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
   echo '/swapfile  none  swap  sw  0  0' | sudo tee -a /etc/fstab
   # убрать из /etc/fstab старую строку swap по /dev/sda5, затем удалить разделы sda5 и sda2:
   sudo parted /dev/sda rm 5
   sudo parted /dev/sda rm 2
   ```
4. Расширить раздел и ФС (ext4 ресайзится онлайн на смонтированном `/`):
   ```bash
   sudo apt-get install -y cloud-guest-utils   # если нет growpart
   sudo growpart /dev/sda 1
   sudo resize2fs /dev/sda1
   df -hT /
   ```

> Диск можно только **увеличивать**, не уменьшать. Перед Вариантом Б — снапшот ВМ обязателен.

### Runbook: расширение RAM `.67`

**Контекст.** ВМ выдано **8 ГБ** (старый `.10` был 4 ГБ). На хосте Dell всего **95.94 ГБ** — расти
есть куда. Сейчас реально занято ~1.5 ГБ, доступно ~6.4 ГБ, своп пустой — необходимости нет,
это на будущее под рост нагрузки.

1. **ESXi (GUI):** VM → Edit Settings → Memory → поднять значение (напр. 8192 → 16384 MB).
   Если ВМ выключена — заодно поставить галку **Memory Hot Plug** (тогда впредь без ребута).

2. **Если Hot Plug включён** — память меняется на живой ВМ, гость подхватывает сам. Проверить:
   ```bash
   free -h
   ```
   Если новые блоки не онлайнулись автоматически — вручную:
   ```bash
   for f in /sys/devices/system/memory/memory*/state; do echo online | sudo tee "$f" >/dev/null; done
   free -h
   ```

3. **Если Hot Plug выключен** (по умолчанию в ESXi OFF) — нужен короткий простой:
   ```bash
   sudo shutdown -h now          # корректно погасить ВМ
   # → в ESXi поднять Memory (+ поставить галку Memory Hot Plug на будущее) → включить ВМ
   free -h                        # проверить после старта
   ```

> Проверить, включён ли Hot Plug: надёжнее всего — галка в ESXi (видна при выключенной ВМ).
